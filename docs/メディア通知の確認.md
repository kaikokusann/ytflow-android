# メディア通知とPiPの確認

## 構成

- `PlaybackService` がGeckoの動画セッション、AndroidのMediaSession、通知を所有する。Activityは同じ動画セッションを表示する。
- GeckoRuntimeはプロセス内で共有し、Activityの作り直しでは終了・再生成しない。
- 再生状態・タイトル・画像・位置はGeckoViewの `MediaSession.Delegate` から受け取る。
- 通知とPiPの操作はGeckoViewの `play()` / `pause()` / `seekTo()` へ送る。指示を送っただけでは再生状態を変更しない。JavaScriptや座標クリックによる予備の制御経路はない。
- 通知本文とMediaSessionの復帰先には同じPendingIntentを使う。URLを伴わない復帰ではページを読み直さない。
- PiPの終了とActivityの非表示が揃った時に一時停止する。PiPに入るだけ、または前面に戻る操作では停止しない。既存の「PiPを閉じたとき一時停止」設定は維持する。
- GeckoのCompositorControllerにもPiP切り替えを通知する。
- 設定DialogはPiP中だけ非表示にし、前面復帰で再表示する。通常のPiP移行では設定ページや未保存入力を破棄しない。
- サムネイルはGeckoViewの画像取得APIを使い、標準メディアカードの背景描画はOSに任せる。
- 動画を開くユーザー操作の時点でmediaPlayback型のフォアグラウンドサービスを開始する。通知権限を再生制御の必須条件にしない。
- 現在ライブかどうかだけは、既存の5秒間隔の再生位置保存メッセージに、現在のプレイヤー応答の `liveBroadcastDetails.isLiveNow` を追加して取得する。動画IDが現在のURLと一致する場合だけ採用する。過去にライブだっただけのアーカイブをライブ扱いしない。
- ライブは通知の時間表示とシークを無効にする。DVR-chanによって有限の長さが返る場合も同様。アーカイブはGeckoの実際の位置・長さ・再生速度を渡す。
- 履歴一覧からアプリを削除した場合は再生と通知を終了する。PiPの×とは区別する。

## 実機確認

2026-11-02、SC-57Gのカバーディスプレイ、debug版 `0.1.1` / `versionCode 2` で確認した。

| 操作 | 確認結果 |
| --- | --- |
| プレイヤー側の一時停止 | 実動画とAndroidの状態がPAUSEDになる |
| アプリ下部の再生ボタン | 実動画とAndroidの状態がPLAYINGになる |
| 通知の再生・一時停止 | アプリを開かず実動画を操作できる |
| アーカイブの通知 | 再生位置と2:13:53の長さが表示される |
| アーカイブの通知シーク | 約15分から約34分へ移動し、実動画も同じ位置になる |
| 通知からの復帰 | 同じ `performance.timeOrigin` と停止位置が維持される |
| PiPの標準× | ライブ・アーカイブ双方で実動画が停止し、MediaSessionと通知が残る |
| ライブの通知 | サムネイルと再生操作が表示され、数日分の時間やシークは表示されない |
| アプリ設定を開いたままPiPへ移る | 設定はPiPに映り込まず、通知から戻ると通常サイズで再表示される |
| 拡張設定を編集中にPiPへ移る | 未保存入力・保存ボタン状態・設定ページを維持する |
| 履歴一覧からアプリを削除 | 再生サービスと通知レコードが終了する |
| 履歴削除後に起動 | 新しいセッションで読み込み・再生でき、再生エラーは出ない |

アーカイブは `h7RgiwLc054`、配信中のライブは `rFZHOHl-L8A` を使用した。ライブのプレイヤー応答で `isLiveNow: true` も確認した。

`assembleDebug` と `lintDebug` は成功。lintには既存の警告があるがエラーはない。
`tests/extension-settings.mjs` の14シナリオと、`tests/media-playback-bridge.mjs` のライブ・アーカイブ・SPA不一致・停止中・保存位置の検証も成功した。
設定を使った試験で変更した未保存入力は元に戻し、保存はしていない。

## 公式YouTubeとの比較

同じ端末の公式YouTubeで、同じライブとアーカイブを開いて比較した。

- アーカイブの通知には時間とシークバーがあり、ライブには時間数値や移動用のつまみがなかった。YTFlowもこの区別に合わせた。
- 公式のPiP×では音声が止まり、通知の再生操作は残った。Android内部の状態はSTOPPEDだった。YTFlowは実動画を一時停止し、PAUSEDとして公開する。
- 両方ともサムネイル付きの標準メディアカードを使う。公式には次の動画ボタンもあるが、YTFlowには未実装の操作を表示しない。

## 残っている差・制約

- **停止中にPiPへ入ると、映像が黒くなるケースが残っている。** GeckoのPiP通知APIを追加しても解消しなかった。再生を開始すると映像は戻る。再生・シークを勝手に発行して描画を促す補助処理は入れていない。
- One UIでは停止後、カードが通知一覧からクイック設定へ移るケースがある。通知レコードとMediaSessionは残り、クイック設定から再生できる。公式と保持時間・表示場所が完全に同一とは確認できていない。
- 履歴一覧からアプリを削除すると、AndroidがGeckoのGPU・補助プロセスも終了することをログで確認した。壊れたプレイヤーの通知を残さないため、ここは明示的な再生終了とした。履歴削除後のバックグラウンド再生継続には対応しない。
- OSによるプロセス終了後の自動再生復元や、長時間のバックグラウンド維持は未検証。終了したプロセスから勝手に再生を始めるサービス再起動は行わない。
- Activity再作成時に古い外部URLを再実行しない修正と、サービス接続前の操作無効化は静的レビューで確認した。Activity強制再作成の自動実機試験は未実施。
